# 项目全功能分析报告

> 日期：2026-07-12  
> 范围：PC 管理后台、H5、微信小程序、移动管理端、API、多租户 SaaS 与部署运维  
> 用途：产品定型、研发排期、商业报价、测试验收和项目交付

## 一、总体结论

本项目应定位为：**以线下活动、报名售票和城市合作伙伴运营为核心，按需扩展会员增长、课程社区、多商户商城和公益生态的多租户 SaaS 平台**。

当前系统已有较广的模块覆盖和可运行主流程，但“有菜单、有页面、有接口”不等于达到商业交付标准。后续应先做实活动主链路和 SaaS 管控，再分模块开放商城、课程社区和公益业务，避免形成大量半完成能力。

建议版本分层：

| 产品层级 | 定位 | 主要功能 |
|---|---|---|
| 核心版 1.0 | 可独立销售交付 | 租户、权限、活动、票种、报名、订单、支付、退款、核销、会员、财务 |
| 增长版 1.5 | 运营增长 | 页面装修、消息触达、标签分群、优惠券、渠道、经营分析 |
| 内容版 2.0 | 学习与社群 | 课程、共学、打卡、证书、论坛 |
| 商业版 2.0 | 多商户交易 | 商户、商品、库存、购物车、订单、物流、售后、结算 |
| 生态版 2.5 | 区域与公益网络 | 城市伙伴、公益项目、大使、合作招募、志愿者 |

商城、课程/社区、公益等必须由平台功能开关和租户套餐共同控制，不应对全部租户默认开放。

## 二、功能完成标准

一个功能只有满足以下条件才算完成：

1. 有明确入口及列表、详情、新增、编辑、停用等必要页面。
2. 主流程、撤销流程、异常流程闭环，不依赖人工改库。
3. 有加载、空数据、失败、无权限、失效、重复提交和重试状态。
4. 后端执行租户隔离、角色权限、套餐权益校验，不能只隐藏前端按钮。
5. 关键状态具有状态机，禁止任意跳转或覆盖历史。
6. 金额、库存、名额、积分写操作具备事务、幂等和并发保护。
7. 关键操作记录操作人、时间、对象及修改前后值。
8. 运营数据可检索、筛选、分页、导出，必要时支持批量操作。
9. 用户应感知的结果有站内信、短信或微信消息通知。
10. 有自动化测试、接口测试、角色化端到端验收和运维保障。

## 三、角色与权限

| 角色 | 主要职责 | 权限边界 |
|---|---|---|
| 平台超级管理员 | 租户、套餐、发布、风险治理 | 可跨租户汇总；跨租户明细访问必须审计 |
| 平台运营/客服/财务 | 审核、客服、平台对账 | 按岗位分权，客服不能改资金，财务不能改内容 |
| 租户管理员 | 本机构全部业务 | 仅本租户，不能绕过套餐和平台开关 |
| 租户运营 | 活动、会员、营销、内容 | 无支付密钥、租户安全和资金结算权限 |
| 租户财务 | 订单、退款、对账、结算 | 业务资料原则上只读，退款支持额度和复核 |
| 核销员 | 扫码及人工核销 | 仅授权活动，不查看完整隐私和财务数据 |
| 商户管理员/店员 | 商品、订单、发货、售后 | 仅所属店铺，不可查看其他商户数据 |
| 讲师/社群管理员 | 课程、共学、内容审核 | 仅被授权课程或社群 |
| 普通会员 | 报名、购买、学习、互动 | 仅本人资产及公开内容 |
| 志愿者/大使/伙伴 | 特定生态任务 | 按项目、区域和合作关系授权 |

最终权限判定应为：**角色权限 + 数据范围 + 套餐权益 + 功能开关**。管理 API 必须从登录身份解析租户，禁止信任客户端传入的 `tenantId`。

## 四、套餐与租户能力

现有试用版、标准版、城市伙伴版、核心伙伴版、定制版可以保留，但需升级为服务端权威权益体系。

| 功能 | 应做成什么样 | 关键验收 | 现状/优先级 |
|---|---|---|---|
| 租户入驻 | 申请、资料审核、初始化管理员、选套餐、开通通知 | 编码唯一；失败可重试；自动初始化角色配置 | 有基础，工作流待完善 / P0 |
| 套餐 | 配置功能、额度、价格、周期、试用和服务等级 | 历史权益不被模板修改误伤；逐请求后端校验 | 模板维度不足 / P0 |
| 配额 | 员工、活动、报名、商品、商户、存储、短信等额度 | 达限提示、扩容、统计口径一致 | 需新增 / P0 |
| 续费到期 | 提醒、续费账单、宽限期、只读期、恢复和数据保留 | 到期不删除交易数据；存量履约可继续 | 需系统化 / P0 |
| 员工账号 | 邀请、停用、重置密码、强制下线、岗位分配 | 停用立即失效；占用额度；操作留痕 | 基础存在 / P0 |
| RBAC | 权限覆盖页面、按钮和 API，支持角色复制、数据范围 | 后端拒绝越权；变更及时生效 | 框架已有 / P0 |
| 数据隔离 | 查询、缓存、导出、任务、文件均按租户隔离 | 覆盖 ID 猜测、导出和异步任务越权测试 | 需安全专项 / P0 |
| 品牌配置 | Logo、主题、联系方式、域名、协议等 | 草稿预览、发布版本、配置审计 | 部分具备 / P1 |

## 七、订单、支付、退款与财务

| 功能 | 应做成什么样 | 关键规则 | 现状/优先级 |
|---|---|---|---|

| 退款 | 申请、审核、原路退款、失败重试、部分退款 | 可退金额准确；独立退款号；累计不超额 | 重点完善 / P0 |

## 十六、核心状态机和数据规则

### 活动

`草稿 -> 待审核 -> 已驳回/待发布 -> 已发布 -> 已结束`，合法阶段可进入 `已取消`。已产生报名的活动禁止物理删除。

### 报名

不要用单一字段表达所有状态，应拆为：

- 审核：待审核、通过、拒绝、无需审核。
- 支付：无需支付、待支付、已支付、部分退款、已退款、已关闭。
- 履约：待参加、已核销、缺席、已取消。

### 商城订单

主单负责支付汇总，子订单按商户履约。子订单为 `待支付 -> 待发货 -> 待收货 -> 已完成`，可进入 `已关闭`。售后采用独立状态机，不能覆盖订单历史。

### 数据生命周期

- 用户注销、租户到期、活动/商品下架都不删除历史交易凭证。
- 上传文件校验类型、大小、访问权限和风险。
- 身份证、手机号、地址、援助材料按最小权限展示。
- 敏感导出记录操作人、生成时间、用途和下载有效期。

## 十八、研发路线图

### P0：商业闭环

1. 收紧全部 API 的租户隔离、RBAC、套餐权益，并补越权测试。
2. 完成活动/报名取消、支付超时、退款失败、重复回调等异常闭环。
3. 实机验收微信支付、短信、微信登录和模板消息。
4. 统一订单、退款、余额、流水口径并建设日对账。
5. 完成扫码、重复核销、人工核销、撤销和弱网验收。
6. 完善审计、迁移、备份恢复、监控告警、发布回滚。
7. 套餐升级为权益和额度体系，补到期续费和只读策略。

### P1：运营效率

活动向导、渠道归因、会员价、报名限制、标签分群、消息触达、首页装修、经营漏斗、客服台、区域授权和伙伴 CRM。商城若准备开放，应优先做库存、拆单、售后、佣金和结算；社区开放前先完成审核举报处罚。

### P2：模块扩展

完成课程学习、共学打卡、证书、论坛、商城常规营销、物流评价，以及经过合规评估后的公益和志愿者模块。

### P3：规模化增强

秒杀、拼团、考试题库、复杂勋章、智能推荐和增长自动化，应在核心业务已有稳定用户和真实数据后建设。

## 十九、最终验收标准

1. 每个销售套餐都有明确功能、额度、限制和到期行为。
2. 平台、租户管理员、运营、财务、核销员、商户、会员完成角色化全流程。
3. 活动创建、审核、发布、报名、支付、审核、核销、退款、对账全链路通过。
4. 任意租户无法通过 URL、接口参数、导出、缓存或任务获取其他租户数据。
5. 支付退款通过正式通道或正式沙箱的验签、回调、查单和补偿测试。
6. 关键列表具备筛选、分页、空态、错误态、权限态，导出与统计一致。
7. 资金、库存、名额、积分通过并发和重复请求测试。
8. 关键配置和管理动作可审计，日志和导出不泄露密钥和敏感信息。
9. 测试、构建、迁移、安全扫描通过，部署制品和版本可追溯。
10. 完成备份恢复及版本回滚演练，并记录实际 RPO、RTO。
11. H5、小程序、PC 后台、移动管理端在目标设备完成主流程测试。
12. 交付包包含源码、环境模板、部署文档、账号清单、教程、测试报告、数据说明、限制清单和验收签字表。

## 二十、最终产品建议

近期重点不是继续增加菜单，而是把“活动 + 报名 + 支付 + 核销 + 财务 + 租户”做成稳定、可审计、可续费的商业闭环。商城、课程社区和公益生态作为独立可售模块，通过功能开关和套餐按需启用。

建议对外表述：

> 面向城市合作伙伴、活动机构和社群组织的一体化活动运营 SaaS，提供活动发布、在线报名售票、会员运营、现场核销、财务对账和多端管理，并可按需扩展课程社区、多商户商城和公益志愿者生态。

该定位与现有代码和页面覆盖相符，也能为后续研发、报价和验收建立清晰边界。
