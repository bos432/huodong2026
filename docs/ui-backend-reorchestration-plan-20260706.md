# UI 与后端重编排方案

更新时间：2026-07-06

适用项目：慢π / 活动报名小程序 + H5 + 管理后台 + API

当前分支基线：`feature/qiwai-ui-experiment`

## 1. 方案结论

当前系统不适合推倒重写，也不适合直接替换成开源活动报名模板。项目已经具备活动、报名、签到、订单、会员、多商家、装修、商城、公益、课程、广告、小程序发布和上线预检等能力，真正的问题是产品主线、后台信息架构和后端模块边界没有跟上功能增长。

本方案采用“保留技术栈、收口产品主线、分阶段重编排”的方式推进：

1. 第一阶段：不大动业务，只重排后台菜单、移动端首页和设计规范。
2. 第二阶段：拆后端 `admin` / `public` 巨型服务，优先拆活动、报名、订单、租户。
3. 第三阶段：商城、公益、广告、课程改成可开关扩展模块。
4. 第四阶段：补齐测试、构建、小程序审核和部署流程。

目标不是把系统做得更复杂，而是把已经堆起来的能力整理成一个运营人员能顺着用、开发人员能继续维护、上线时能验证回滚的产品。

## 2. 当前诊断

### 2.1 产品层

原始主线是活动报名，但当前已经扩展为文化活动 SaaS：

- 用户端：活动、专题内容、共修、商城、公益、大使、城市合伙人、我的报名、订单、钱包。
- 后台端：平台监管、商家工作台、活动审核、装修、广告、商城、财务、会员、公益、课程、小程序发布、上线体检。
- 后端：多租户、支付、退款、会员积分、商城交易、广告结算、通知、文件上传、运维预检。

问题不在于功能多，而在于功能缺少主次。用户和运营人员进入系统后，最核心的“发布活动 -> 报名 -> 支付/确认 -> 签到 -> 复盘”没有被稳定地放在第一层。

### 2.2 后台 UI 层

代表文件：

- `apps/admin/src/views/Layout.vue`
- `apps/admin/src/router.ts`
- `apps/admin/src/views/HomepageBuilder.vue`

主要问题：

- 菜单组和业务域集中写在 `Layout.vue`，平台端和商家端入口数量多，后续维护成本高。
- 路由定义集中在 `router.ts`，权限、scope、fallback、模块开关逻辑混在一起。
- 页面粒度不均衡，个别页面承担太多编辑器和业务逻辑，例如首页装修。
- 后台全局样式偏轻，缺少统一的信息密度、筛选区、表格区、详情抽屉、空态和危险操作规范。

### 2.3 移动端 UI 层

代表文件：

- `apps/mobile/src/pages/index/index.vue`
- `apps/mobile/src/pages.json`
- `apps/mobile/src/styles.css`
- `apps/mobile/src/components/TabBar.vue`

主要问题：

- 首页同时承载品牌故事、院长招募、大使申请、帮扶申请、商城、课程、共修动态等入口，活动报名主线被稀释。
- 当前“新中式”色彩基础可保留，但页面信息优先级需要重新排序。
- 小程序审核对“课程、教育、售价、培训”等表达敏感，移动端重排必须继续保持审核安全文案。
- 底部导航和首页装修已有动态配置能力，改版应尊重已有后台装修数据和显式禁用逻辑。

### 2.4 后端层

代表文件：

- `apps/api/src/modules/app.module.ts`
- `apps/api/src/modules/admin/admin.controller.ts`
- `apps/api/src/modules/admin/admin.service.ts`
- `apps/api/src/modules/public/public.controller.ts`
- `apps/api/src/modules/public/public.service.ts`
- `apps/api/src/modules/mall/mall.service.ts`

主要问题：

- 实体很多，但业务模块少，领域边界没有随功能增长同步拆分。
- `admin.controller` 和 `admin.service` 覆盖商家、活动、订单、财务、公益、广告、小程序发布等太多职责。
- `public.controller` 同时承载登录、活动、支付、课程、商城、公域内容等入口。
- 巨型 service 导致回归风险大：修改活动保存，可能影响租户、订单、财务、通知或装修。

## 3. 目标产品主线

### 3.1 用户端主线

用户端第一优先级固定为活动参与闭环：

1. 发现活动：城市 / 商家 / 分类 / 推荐活动。
2. 查看详情：时间地点、名额、报名条件、票种、入群说明。
3. 报名下单：填写资料、选择票种、优惠 / 积分 / 会员权益。
4. 支付或确认：微信支付、余额、线下确认。
5. 我的报名：状态、订单、入群提示、签到码。
6. 现场签到：二维码 / 签到码核销。
7. 活动后复盘：评价、心得、再次报名。

课程、商城、公益、大使、广告属于运营扩展，不应抢占活动主线。

### 3.2 后台主线

后台第一优先级固定为商家运营闭环：

1. 工作台：今日待办、待审核报名、待收款订单、待签到活动。
2. 活动：创建、编辑、发布、审核记录、活动二维码 / 链接。
3. 报名：报名列表、审核、候补、导出。
4. 签到：扫码核销、签到记录。
5. 订单财务：订单、退款、对账、收款账户。
6. 会员运营：会员、标签、通知、评价。
7. 装修营销：公告、首页装修、弹窗、活动复盘。

平台超级管理员另有监管主线：

1. 平台概览。
2. 商家开通和权限。
3. 活动审核和内容监管。
4. 财务监管和结算。
5. 扩展模块授权。
6. 系统、发布、审计、上线体检。

## 4. 设计原则

1. 不推倒重写：保留 Vue 3、Element Plus、uni-app、NestJS、TypeORM、MySQL。
2. 先体验后结构：第一阶段优先改善运营入口、首页主线和视觉规范，不改变核心业务语义。
3. 保持兼容：后端拆分时优先保持现有接口路径和响应结构，前端无感迁移。
4. 扩展降噪：商城、公益、广告、课程等能力默认按租户能力开关显示，不在主流程里硬塞入口。
5. 权限前后端一致：菜单隐藏只是体验，后端 guard / tenant scope 仍是最终边界。
6. 小程序审核安全：移动端文案继续规避教育课程销售敏感表达。
7. 每阶段可验收、可回滚：每次改动都有构建、烟测和人工验收口径。

## 5. 第一阶段：UI 与信息架构重排

目标：不大动业务逻辑，只让系统从“功能堆叠”变成“按角色和任务进入”。

### 5.1 后台菜单重排

建议把后台菜单配置从 `Layout.vue` 抽离为独立配置：

- 新增：`apps/admin/src/navigation/admin-menu.ts`
- 保留：`Layout.vue` 只负责渲染 shell、租户切换、用户状态、菜单组件。
- 后续可新增：`apps/admin/src/navigation/route-catalog.ts`，让菜单和路由共用同一份模块元信息。

平台端一级分组建议：

| 分组 | 主要入口 |
| --- | --- |
| 平台总览 | 全局数据看板、数据中心、客服查询 |
| 商家管理 | 商家列表、区域保护、商家账号、权限配置 |
| 活动监管 | 活动审核、全部活动、全局报名、公告监管、全局分类 |
| 财务监管 | 全局订单、全局对账、商家收款账户、结算 |
| 扩展模块 | 商城、课程/共修、公益、大使、广告 |
| 系统安全 | 系统设置、上线体检、小程序发布、日志、运维教程 |

商家端一级分组建议：

| 分组 | 主要入口 |
| --- | --- |
| 工作台 | 今日待办、数据概览、客服查询 |
| 活动运营 | 活动管理、分类、票种、优惠码 |
| 报名签到 | 报名管理、候补、签到核销 |
| 订单财务 | 订单、财务对账、收款方式、代理结算 |
| 会员运营 | 会员、标签、通知、评价 |
| 装修营销 | 首页装修、公告、营销弹窗、活动漏斗、活动复盘 |
| 扩展模块 | 商城、专题内容、共修、公益，按开关显示 |
| 设置 | 商家资料、员工账号、操作日志、运营设置 |

第一阶段验收标准：

- 平台账号登录后，第一屏只看到平台监管相关入口。
- 商家账号登录后，第一屏只看到商家经营相关入口。
- 财务、签到等角色菜单文案仍符合已有权限定位。
- 商城未启用的商家不显示商城入口。
- 原有路由仍可通过地址访问时被权限正确拦截或放行。

### 5.2 后台视觉规范

保留 Element Plus，不引入新的大型后台框架。

统一以下页面结构：

1. 页面标题区：页面名、说明、主操作按钮。
2. 筛选区：搜索、状态、商家、日期，统一放在表格上方。
3. 数据区：表格、分页、批量操作。
4. 详情区：优先使用抽屉，不让列表页承担过多弹窗。
5. 危险操作：删除、退款、停用、驳回必须二次确认，并展示影响。
6. 空态：告诉运营下一步应该做什么，不只显示“暂无数据”。

第一阶段建议先改这些页面的壳层和入口，不深改业务：

- `Dashboard.vue`
- `Activities.vue`
- `Registrations.vue`
- `Orders.vue`
- `Finance.vue`
- `HomepageBuilder.vue`
- `SystemSettings.vue`

### 5.3 移动端首页重排

移动端首页建议从“品牌门户混合页”调整为“活动优先首页”：

1. 顶部：当前城市 / 商家、搜索、消息或我的报名快捷入口。
2. 主行动区：近期可报名活动、我的报名状态、签到码入口。
3. 活动分类：沙龙、读书会、体验、公益、亲子等，按运营配置展示。
4. 推荐活动：优先展示可报名、即将开始、名额紧张的活动。
5. 专题内容 / 共修动态：作为次级内容流。
6. 商城 / 公益 / 大使：作为运营卡片或底部二级入口，按开关显示。

底部导航建议：

| Tab | 定位 |
| --- | --- |
| 首页 | 活动发现和运营推荐 |
| 活动 | 活动列表、筛选、搜索 |
| 共修 | 动态、打卡、心得 |
| 我的 | 我的报名、订单、签到码、资料 |

如果商城是当前商家重点经营能力，可作为装修配置中的第五个 Tab，而不是全局硬编码。

### 5.4 移动端视觉规范

保留当前新中式基础，但做克制化：

- 背景继续使用米白，但减少卡片堆叠和 emoji 图标依赖。
- 主色继续使用朱砂红，主要用于报名、支付、申请等关键动作。
- 石青用于次级标签、分类和信息提示。
- 活动卡片优先展示真实封面、时间、地点、剩余名额和状态。
- 首页标题和模块标题减少装饰符号，避免显得像临时模板。
- 审核敏感文案继续用“专题内容、活动资料、参与权益、观看进度”等中性表达。

第一阶段涉及移动端代码时，必须执行：

```powershell
npm --prefix apps/mobile run build:mp-weixin
npm --prefix apps/mobile run build:h5
```

并在交付结论中明确：修改 `apps/mobile` 后需要重新上传体验版并提交微信审核。

## 6. 第二阶段：后端模块拆分

目标：在不改变接口行为的前提下，把巨型 `admin` / `public` 服务拆成可维护的业务域。

### 6.1 优先拆分顺序

第一批只拆核心主线：

1. 租户域：商家、区域、租户上下文、租户权限。
2. 活动域：活动、分类、字段、审核记录、活动详情模块。
3. 报名域：报名、候补、审核、签到码。
4. 订单域：订单、票种、优惠码、退款、支付状态。

第二批再拆运营域：

1. 会员域：会员档案、等级、积分、标签。
2. 装修域：首页模块、模板、版本、公告、弹窗。
3. 通知域：通知模板、发送记录、提醒规则。
4. 财务域：支付流水、对账、导出、代理结算。

第三批拆扩展域：

1. 商城域。
2. 课程 / 专题内容域。
3. 共修 / 社区域。
4. 公益 / 志愿者域。
5. 广告域。
6. 小程序发布域。

### 6.2 目标模块结构

建议逐步演进为：

```text
apps/api/src/modules/
  auth/
  tenants/
  activities/
  registrations/
  orders/
  payments/
  members/
  homepage/
  notifications/
  finance/
  system/
  public-bff/
  admin-shell/
  extensions/
    mall/
    academy/
    charity/
    ads/
    miniprogram-release/
```

说明：

- `admin-shell` 只处理后台登录态、当前管理员、菜单能力和通用后台上下文。
- `public-bff` 只承接公开端聚合接口，不直接沉淀复杂业务规则。
- 具体业务规则进入 `activities`、`registrations`、`orders` 等领域服务。
- `extensions` 下模块必须支持按租户能力开关显示和调用。

### 6.3 拆分策略

每次只拆一个领域，避免大范围行为漂移：

1. 先复制接口测试或 smoke 场景，固定当前行为。
2. 新增领域 service，把纯业务逻辑迁出巨型 service。
3. controller 方法先保持路径不变，只把调用转发到新 service。
4. DTO 按领域拆文件，但导出兼容旧 import。
5. 完成后跑 API 单测、构建和相关 smoke。

后端拆分不应在同一批次里重命名接口、改返回结构、改数据库字段，除非明确记录迁移和兼容策略。

### 6.4 核心横切能力

拆分时以下能力必须保留为共享基础设施：

- 租户上下文解析。
- 管理员权限和角色 guard。
- 操作日志。
- 文件上传和上传目录策略。
- 支付 provider 和回调验签。
- 导出 Excel。
- 错误响应和 requestId。
- 生产配置检查和上线体检。

## 7. 第三阶段：扩展模块可开关治理

目标：让商城、公益、广告、课程等能力成为“可授权、可隐藏、可部署验收”的扩展，而不是所有商家默认背负的复杂度。

### 7.1 扩展模块清单

| 模块 | 当前定位 | 重编排后定位 |
| --- | --- | --- |
| 商城 | 完整交易体系 | 商家可选扩展，默认不抢活动主线 |
| 课程 / 专题内容 | 内容售卖与学习 | 小程序审核安全表达下的内容扩展 |
| 共修 / 社区 | 动态、心得、打卡 | 活动后留存和社群运营扩展 |
| 公益 / 志愿者 | 公益池、志愿任务 | 平台品牌与活动扩展 |
| 广告中心 | 商业化投放 | 高级运营扩展 |
| 文化大使 / 合伙人 | 招募和招商 | 平台侧增长扩展 |

### 7.2 开关体系

建议形成统一扩展开关：

- 后端租户能力字段控制接口写入和读取。
- 后台菜单按能力开关显示。
- 移动端首页和底部导航按装修配置 + 能力开关显示。
- smoke / preflight 对启用模块执行专项验收。

第一批建议先治理商城和课程，因为它们对首页、菜单、支付和小程序审核影响最大。

## 8. 第四阶段：测试、构建、审核与部署

### 8.1 基础验证

每个阶段至少执行：

```powershell
npm --prefix apps/api run build
npm --prefix apps/admin run build
```

涉及移动端时增加：

```powershell
npm --prefix apps/mobile run build:mp-weixin
npm --prefix apps/mobile run build:h5
```

涉及后端核心接口时增加：

```powershell
npm --prefix apps/api run test
npm run smoke
npm run smoke:flow
```

涉及多租户、商城、真实支付、上线挡板时，按现有维护文档执行对应 smoke 和 preflight。

### 8.2 人工验收主流程

每轮改动至少覆盖：

1. 平台超管登录后台，查看商家、活动监管、财务监管、系统安全。
2. 商家管理员登录后台，发布活动、查看报名、订单、签到。
3. 财务角色登录后台，确认线下收款或查看对账。
4. 签到角色登录后台，扫码或输入签到码核销。
5. 普通用户在 H5 / 小程序查看活动、报名、进入我的报名、查看签到码。
6. 如果改了移动端，使用微信开发者工具或体验版复测首页、报名、我的、登录和底部导航。

### 8.3 小程序审核规则

- 只改 `apps/api`、`apps/admin`、`docs`：通常不需要重新提交小程序审核。
- 改 `apps/mobile` 或小程序构建脚本：需要重新构建小程序、上传体验版并提交微信审核。
- 改线上装修数据但不改代码：一般不需要审核，但要真机或开发者工具确认展示结果。
- 移动端继续避免“课程、题库、答案、培训、教育、售价、报名费、付费课程”等容易触发审核误判的表达。

## 9. 建议执行排期

### 阶段 0：准备和基线固定，1-2 天

- 固定当前分支状态、运行基础构建。
- 确认后台、H5、小程序当前可访问路径。
- 梳理核心角色账号和验收数据。
- 建立本方案执行记录。

验收结果：

- 当前系统可构建。
- 当前主流程问题已记录，不把历史问题误归因到重编排。

### 阶段 1：UI 与信息架构，3-5 天

## 11. 风险和控制

| 风险 | 控制方式 |
| --- | --- |
| 菜单重排导致入口找不到 | 保留路由路径，先只改分组和展示，增加角色验收 |
| 小程序审核再次误判 | 移动端继续使用中性文案，改动后真机 / 开发者工具检查 |
| 后端拆分引入行为变化 | 每次只拆一个领域，接口路径和响应结构保持兼容 |
| 多租户边界回退 | 拆分时保留 tenant scope 测试和 smoke |
| 商城等扩展影响主流程 | 扩展入口统一按能力开关隐藏，主流程不依赖扩展 |
| 巨型页面迁移过大 | 第一阶段不拆页面内部复杂表单，只先抽菜单和壳层 |

## 12. 成功标准

完成重编排后，系统应达到以下状态：

1. 新运营人员能在 5 分钟内知道活动发布、报名审核、签到、订单在哪里。
2. 平台超管和商家管理员看到的是不同工作台，不再混淆监管和经营。
3. 用户端首页第一屏明确指向活动参与，而不是多个业务入口平均铺开。
4. 后端活动、报名、订单、租户核心逻辑有独立服务承载。
5. 商城、公益、广告、课程等扩展按商家能力显示，不干扰未启用商家。
6. 每次上线都有构建、smoke、小程序审核和部署说明，不靠记忆交付。
