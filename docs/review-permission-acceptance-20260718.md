## 2. 权限模型

| 权限 | 能力 |
|---|---|
| `review.view` | 查看当前商家和岗位活动范围内的评价、举报、脱敏会员信息和活动选项 |
| `review.manage` | 回复、精选、隐藏评价和处理举报，自动包含 `review.view` |
| `review.sensitive` | 查看完整会员手机号和举报处理人，自动包含 `review.view`，不包含写权限 |

维护与敏感权限互不包含。运营人员可以处置内容而不自动获得完整会员手机号；敏感审阅账号也不能回复、隐藏、精选或处理举报。

## 3. 本轮发现并修复的问题

### 3.1 单一 manage 权限

原页面和接口统一依赖 `review.manage`，无法建立只读、内容处置和敏感信息审阅的最小权限账号。现拆为查看、维护、敏感三项权限，并同步 API、PC 权限目录、路由、菜单、默认运营角色和演示 seed。

### 3.2 列表缺少专属 options 和独立分页

现新增评价专属活动 options，仅返回当前商家和岗位 `activity_ids` 范围内的最小活动对象。评价和举报分别维护页码、加载状态、错误状态与重试，每页最多 100 条；非法状态和分页参数返回 400。

### 3.3 响应实体过宽和手机号明文

评价、举报、活动、会员、报名和处理人统一改为显式字段选择与白名单 DTO。普通查看和维护账号的手机号由服务端固定脱敏，PC 再使用 `maskPhone` 二次保护；只有 `review.sensitive` 可以查看完整手机号和举报处理人。

自动化验收扫描 `passwordHash/openid/unionid/settings/answers/formSnapshot/checkInCode/eligibilityRules/sessionVersion`，均未出现在管理响应中。

### 3.4 处置状态缺少并发保护

评价和举报处置均在事务中使用 `pessimistic_write` 行锁，并在锁后复核状态。举报仅允许从 `pending` 进入 `resolved/rejected`，处理说明必填且最长 500 字；管理员回复最长 255 字。

真实并发验收中，同一举报的两次处置返回 `200/400`，仅一次生效；再次处置已完成举报固定返回 400。

### 3.5 隐藏与精选状态可能冲突

评价被隐藏时会自动取消精选。举报成立并选择隐藏评价后，最终评价状态为 `hidden`、`featured=false`，管理员回复继续保留。

### 3.6 缺少统一审计和严格租户边界

评价处置和举报处理分别写入 `review.moderate`、`review_report.handle` 操作审计。商家账号猜测其他商家评价 ID 或访问岗位范围外对象均返回 404。
