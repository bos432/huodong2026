## 专项验收

命令：

```powershell
npm run acceptance:mall-after-sale
```

结果：

- 同一业务键两路并发申请只生成售后单 63 一条记录。
- 仅退款 63：审核后 `approved`，线下退款流水成功。
- 退货退款 64：用户举证并申请平台介入，平台同意后进入待寄回，用户填写寄回物流，商家收货后完成退款。
- 换货 65：审核、寄回、商家收货、换货发货、用户签收后进入 `approved`。
- 三张售后单各有一条商品数量明细，共 13 条协商/状态时间线。
- 使用杭州租户上下文读取演示中心售后单返回 404。
- 后台响应不含 `passwordHash`、OpenID、UnionID、内部业务快照或未清洗渠道报文。

## 整改记录

1. 修复确认收到退货时 TypeORM eager relation 级联触发 MySQL 61 表 join 上限。
2. 修复换货发货锁查询未加载租户，导致换货包裹 `tenantId` 为空。
3. 修复用户确认换货收货时售后时间线缺少租户关系，导致消息插入失败。
4. 后台售后 DTO 改为显式白名单，手机号脱敏并移除用户认证字段、订单内部业务快照。
5. `mall-after-sale-acceptance` 从参数化骨架升级为自登录、自建订单和可重复执行的完整专项脚本。
