# 慢π全平台 UI 与产品升级设计规格

**日期：** 2026-10-02  
**状态：** 设计已由用户确认，待书面规格审阅  
**目标：** 在不破坏现有业务、接口、数据库、多租户和生产兼容性的前提下，完成慢π用户端、管理后台、核心 API、Worker 和发布治理的渐进式升级。

## 1. 已确认决策

- 产品优先级：以“发现活动 → 报名 → 支付 → 参加 → 签到 → 评价/分享 → 再次报名”的活动闭环为最高优先级。
- 架构路线：采用模块化单体渐进重构，不立即拆分微服务，不整体重写。
- 兼容边界：保留现有数据库、历史数据、公开 API 路径、主要响应结构、页面路由、后台菜单、多租户隔离、权限规则和报名/支付/退款/签到/通知能力。
- 发布策略：本地验证 → H5/后台回归 → 微信开发者工具体验版 → 真机验收 → 生产备份 → 新实例 → readiness → 灰度 → 观察 → 全量；异常时可回滚。
- 外部能力：真实短信、微信订阅消息、正式支付、正式退款、对象存储、生产 Worker 和微信真机不能以本地 mock 结果替代。
- 数据原则：不删除、清理或回滚现有测试数据；不触碰其他站点、生产数据库或无关租户。

## 2. 范围与非目标

### 2.1 本次范围

1. 微信小程序用户端 UI 和活动闭环。
2. H5 用户端 UI 和活动闭环。
3. 管理后台运营工作台、活动编辑器、首页装修、通知中心和内容治理。
4. 活动、报名、订单、退款、租户、会员、通知、社区和分析模块的内部边界整理。
5. 独立 `activity-worker` 的任务、幂等、重试、死信、监控和生产部署。
6. 共享类型和请求/错误/租户上下文契约。
7. 三端验收、真实外部能力验证、灰度和回滚演练。

### 2.2 明确不做

- 不立即拆成微服务。
- 不拆分数据库或更换技术栈。
- 不整体重写商城、专题、社区或手机管理端。
- 不在报名主链路之前强行加入未经审核的聊天、社交证明或位置共享。
- 不使用虚假报名人数、虚假头像或无法验证的评价。

## 3. 总体架构

```text
微信小程序 / H5
          │
管理后台 ──┼── 兼容 API Controller
          │
          ├── activity
          ├── registration
          ├── commerce
          ├── tenant
          ├── membership
          ├── notification
          ├── community
          ├── analytics
          └── 兼容旧业务模块
                    │
                 MySQL
                    │
             activity-worker
```

保留原 Controller 作为兼容入口，内部逐步将大 Service 拆成业务模块。每次只迁移一个业务边界，旧 Service 暂时保留适配层，完成测试和灰度后再决定是否下线。

### 3.1 模块拆分顺序

1. `activity`
2. `registration`
3. `commerce`
4. `notification`
5. `membership`
6. `community`
7. `analytics`
8. 课程、商城、公益、志愿者、城市合伙人等边缘模块

### 3.2 共享契约

`packages/shared` 逐步提供以下跨端声明，不直接暴露数据库实体：

```text
PublicActivitySummary
PublicRegistrationSummary
PublicOrderSummary
PublicNotificationRecord
TenantContext
MemberSnapshot
NotificationChannel
NotificationScene
PostEventAutomationSettings
```

API 因 `rootDir` 限制不能直接引用 shared 源码时，使用构建后的声明文件或独立契约包，不通过不受控的跨目录 import 规避编译边界。

## 4. 用户端 UI 设计

### 4.1 视觉基线

- 慢π青绿色：主操作、链接、选中态。
- 深蓝黑：标题和关键决策信息。
- 暖红/暖橙：价格、退款、风险和紧急状态。
- 浅灰背景、白色内容面。
- 圆角统一 8px；间距使用 8/12/16/24px。
- 不使用伪造头像、虚假人数、自动轮播、强制视差或高频粒子效果。
- 所有页面具备加载、空态、错误、重试、提交中和成功反馈。

### 4.2 首页

首页按“先发现，再报名”组织：

```text
当前城市 / 商家切换 / 搜索
主推活动
活动分类横向滚动
按日期分组的活动流
活动回顾入口
```

主推活动必须显示封面、日期、标题、时间、地点、价格、报名状态和真实名额/报名信息。结束活动默认不进入首页主推荐，仅从活动回顾、个人记录或历史筛选进入。无活动时展示明确空态和订阅/浏览入口。

### 4.3 列表与详情

列表统一显示封面、日期、标题、时间地点、价格、报名状态和名额信息，支持搜索、筛选、分类、分页/加载更多、失败重试和空态。

详情首屏固定为：

```text
封面 → 活动状态 → 日期时间 → 地点 → 价格 → 剩余名额 → 主办方
```

底部固定操作严格对应真实状态：`立即报名`、`报名并支付`、`加入候补`、`报名已结束`、`报名已完成`。

### 4.4 报名、支付和活动空间

报名页采用“填写报名信息 → 确认订单 → 支付/提交”三步流程，具备步骤提示、防重复提交、提交中状态、支付失败重试、未支付订单复用、审核提示和候补状态。

报名成功后进入活动空间，包含公告、脱敏成员摘要、问答、签到、地点、受控群二维码、客服和分享。问答支持审核和举报，不建设未经审核的实时群聊和位置共享。

### 4.5 活动结束后的内容链路

活动结束后，真实报名记录关联的用户才能进入“评价活动 → 上传照片 → 发布心得 → 审核 → 活动回顾”。内容状态和举报结果可追踪，未参加用户不能伪造履约内容。

### 4.6 我的与订单

“我的”顶部展示身份、会员等级、积分和权益；中部展示待参加、待处理、退款售后、优惠券等任务入口；下方展示报名活动、活动记录、评价、浏览足迹、常用报名人、社区/社交和设置。订单页统一登录拦截、加载、空态、失败、返回路径和底部导航。

### 4.7 动效

统一使用：

```text
apps/mobile/src/motion/motion.ts
apps/mobile/src/motion/entrance.ts
apps/mobile/src/motion/bottom-sheet.ts
apps/mobile/src/motion/media.ts
apps/mobile/src/motion/platform-adapter.ts
```

H5 和后台可使用 GSAP；微信端只通过安全适配层使用可编译的 transform/opacity 动效，禁止依赖 `window`、`document`、DOM 或 ScrollTrigger。Vue 组件卸载时清理动画上下文，并支持减弱动效。

## 5. 管理后台与内容治理

### 5.1 运营工作台

后台首页展示可操作的待处理事项、活动经营、订单与退款、通知失败、Worker 积压、会员召回和城市经营，不堆叠无行动意义的统计卡片。

### 5.2 活动编辑器

保留现有字段和菜单路径，通过分步引导组织为：基础信息、时间地点、封面和详情、报名字段、票种和价格、活动空间、发布检查。发布检查区分阻断问题和完善建议；阻断问题未解决不能发布，完善建议允许保存草稿。

上传的封面、二维码和详情图片必须有上传中、成功、失败和重新上传状态。

### 5.3 首页装修

装修器支持模块排序、主推活动、日期活动流、分类、回顾和订阅入口，支持展示变体、数量、历史活动开关、预览高亮、操作人、租户、版本和发布时间。预览复用用户端真实组件和状态逻辑。

### 5.4 通知中心

通知场景可独立启停，至少包括报名成功、待支付、活动变更/取消、退款结果、签到提醒、活动结束评价邀请、同类活动推荐和会员召回。后台明确区分站内通知、短信和微信订阅消息；未配置模板、授权、密钥和真实环境验证时不能显示为“已发送”。

### 5.5 内容与权限

社区、心得、图片和动态统一使用 `草稿 → 待审核 → 已通过/已拒绝 → 已隐藏/已删除 → 申诉中` 状态。所有审核、举报、删除、隐藏、申诉、危险配置和租户切换保留操作日志。后台操作同时校验用户身份、角色权限、租户范围、资源归属和当前状态。

## 6. 活动闭环与 Worker

### 6.1 核心数据流

```text
活动发现
  → 活动详情
  → 报名信息
  → 创建或复用订单
  → 支付
  → 报名确认
  → 活动空间
  → 签到
  → 评价/照片/心得
  → 同类活动推荐
```

支付回调、退款回调、报名提交和通知发送都必须幂等。所有受限活动空间访问必须经过报名或权限校验。

### 6.2 Worker 范围

独立 `activity-worker` 处理短信、微信订阅消息、订单关闭、支付/退款同步、活动生命周期、活动结束自动运营、会员积分/等级、会员召回和统计重算。

每个任务包含：

```text
taskId, tenantId, scene, idempotencyKey, requestId,
attempt, nextRunAt, status, lastError
```

任务状态为 `queued`、`processing`、`succeeded`、`retrying`、`dead` 或 `cancelled`。任务有锁、最大重试次数、指数退避、死信和后台手动重试。模板不存在、用户未授权、手机号无效、租户未配置和外部明确拒绝等不可恢复错误不能无限重试。

### 6.3 监控

至少监控 API 成功率、5xx、响应时间、报名转化、支付成功率、退款失败率、通知成功/重试/死信、队列积压、Worker 心跳、对象存储失败和多租户异常访问。

## 7. 分阶段交付

### R0：现状审计与基线冻结

**交付：** 测试和构建基线、公开 API 清单、页面路由清单、租户/权限矩阵、外部能力状态、性能和错误基线。  
**门禁：** 不修改业务逻辑；现有测试、构建、preflight 和 readiness 可重复运行。

### R1：统一 UI 设计系统与动效适配

**交付：** 移动端/后台令牌、公共空态和状态组件、动效适配层、底部导航、活动卡片和加载错误规范。  
**门禁：** H5 与小程序构建通过；微信端无 DOM 依赖；375/390/760px 无溢出。

### R2：活动发现

**交付：** 首页主推活动、日期流、分类、搜索、列表筛选、活动状态、真实名额和结束活动入口。  
**门禁：** 首页不展示已结束活动作为推荐；租户和城市切换不串数据。

### R3：报名与订单

**交付：** 详情、报名三步流程、候补、订单复用、支付失败重试、订单状态和固定 CTA。  
**门禁：** 免费/付费报名、防重复提交、支付回调和订单状态机通过测试。

### R4：履约与活动空间

**交付：** 活动空间、公告、成员脱敏、问答、签到、二维码、客服、分享、活动回顾。  
**门禁：** 无权限不能进入；签到、问答审核、举报和结束后入口状态正确。

### R5：后台运营与装修

**交付：** 运营工作台、活动编辑器视觉分步、发布检查、首页装修排序和预览、上传状态。  
**门禁：** 旧菜单和权限不变；预览顺序与用户端一致；阻断问题不能发布。

### R6：内容沉淀与社交治理

**交付：** 评价、照片、心得、社区发布、审核、举报、隐藏、申诉、社交资料和隐私控制。  
**门禁：** 只有真实参与用户可发布履约内容；内容不作为未经审核的社交证明。

### R7：会员、积分、召回与自动运营

**交付：** 会员等级/权益真实性、积分流水、活动结束运营、同类推荐、30/60/90 天召回和后台开关。  
**门禁：** 站内通知、短信、微信订阅消息状态分离；开关不会在未配置外部渠道时误报成功。

### R8：API 共享契约与 Worker

**交付：** 核心共享类型、统一请求/错误/租户上下文、业务模块适配层、独立 Worker、任务幂等、重试、死信和积压监控。  
**门禁：** Worker 重启不丢任务；重复执行不产生重复订单、通知或积分；旧 API 兼容。

### R9：灰度、真实能力与上线

**交付：** 对象存储、短信、微信订阅消息、正式支付/退款、生产 Worker、体验版、真机验收、灰度和回滚记录。  
**门禁：** 数据库和静态资源备份；readiness 通过；完成一次灰度和一次回滚演练；生产版本和提交哈希可追溯。

## 8. 测试与验收

### 8.1 自动化测试

覆盖活动状态、报名资格、名额候补、订单状态、支付/退款幂等、通知开关、Worker 重试/死信、会员积分/召回、审核状态和多租户隔离。

### 8.2 三端测试

- H5：375px、390px、760px，控制台无错误、无横向溢出、固定栏和深链稳定。
- 微信开发者工具：合法域名、登录、浏览、免费/付费报名、候补、订单、活动空间、分享、订阅授权和过审/正式模式。
- 微信真机：冷启动、低网速、拒绝授权、支付取消、上传失败、扫码签到、二维码识别、分享返回、底部导航和安全区。

### 8.3 真实环境记录

每项真实能力记录环境、租户、测试账号、时间、请求 ID、外部响应、后台记录、用户端表现和结论。未完成真实能力验证前，结论只能写“本地/测试环境通过”。

## 9. 风险与回滚

高风险项是支付/退款状态、通知重复发送、多租户串数据、Worker 积压、小程序请求域名和对象存储权限。灰度期间保留旧路径和功能开关，出现异常时依次关闭新开关、停止新 Worker 消费、恢复旧 API/静态资源、保留失败任务和日志、核对业务数据后再修复重灰度。禁止通过删除订单、任务或测试数据掩盖问题。

## 10. 完成定义

只有当 R0–R9 的交付物和门禁全部通过，核心活动闭环、三端构建、微信工具/真机、真实短信/订阅消息/支付/退款/对象存储、Worker 重启/重试/死信、权限/租户/审核、灰度和回滚全部有证据，并且任务执行记录和生产版本可追溯时，才能宣称整套计划完成。
