## 一、发布决策

当前建议为 **No-Go**。以下三项完成并回归前，不发布生产：

1. 核心交易写入成功后不得因积分、通知等后置副作用返回失败。
2. 公益保留退款完成后必须关闭报名资格，并禁止重复退款、签到和活动空间访问。
3. 修复 H5 页面切换 `rootRef.value` 空引用错误。

## 二、P0 整改

### P0-1 核心事务与积分副作用解耦

**根因**

- `MemberPointsService.awardEvent()` 在找不到规则时直接抛出“积分规则不存在”。
- `AdminService.confirmOfflinePayment()` 先在事务中保存订单和报名，再在事务外发放积分。
- 核销流程同样先提交核销事务，再调用积分服务。
- 因此数据库已成功，接口却返回 400，前端认为操作失败。

**涉及代码**

- `apps/api/src/modules/member-points/member-points.service.ts`
- `apps/api/src/modules/admin/admin.service.ts` 的 `confirmOfflinePayment()` 和签到核销逻辑
- `apps/api/src/modules/public/public.service.ts` 的支付成功积分逻辑

**整改方式**

1. 为每个租户创建完整积分规则；迁移和租户创建流程必须自动初始化规则。
2. 业务事件发积分改为可靠异步任务，使用幂等键：
   - `points:activity_order_paid:{orderId}`
   - `points:activity_check_in:{checkInId}`
3. 找不到积分规则时记录 `skipped/misconfigured` 运维事件，不污染支付或核销主接口。
4. 支付、核销主响应只由核心事务结果决定；通知、积分、分析写入失败进入 Worker 重试/死信。
5. 前端收到超时或 5xx 后应先按订单/报名 ID 查询真实状态，再允许重试。

**必须新增测试**

- 无积分规则时确认收款仍返回 200，订单只确认一次。
- 无积分规则时核销仍返回 200，核销记录只创建一次。
- 积分任务补齐规则后可重试成功，且不重复加分。
- 接口超时后前端刷新能识别“实际已成功”。

### P0-2 公益保留退款定义为业务终态

**根因**

- `RefundCompletionService` 仅在累计退款达到订单全额时把订单设为 `refunded` 并取消报名。
- 公益保留退款金额天然小于订单金额，所以订单成为 `partially_refunded`，报名继续 `approved`。
- 退款预览仍按原订单金额计算，导致剩余公益金再次显示为可退。

**涉及代码**

- `apps/api/src/modules/refund-completion.service.ts`
- `apps/api/src/modules/charity-fund.service.ts` 的 `previewRetainedActivityRefund()`
- `apps/mobile/src/pages/user/registration.vue`

**整改方式**

1. 在退款记录或业务快照增加明确策略字段，如 `refundPolicy=charity_retained_terminal`，不要仅依赖 reason 文本。
2. 该类退款完成后：
   - 会计订单可保留 `partially_refunded`；
   - 报名必须变为 `cancelled/refunded`；
   - 立即释放活动名额；
   - 禁止签到码、活动空间成员权限和再次退款；
   - 用户仍可从历史记录查看只读报名与退款明细，不能返回含糊的“报名记录不存在”；
   - 保留公益基金计提和审计链。
3. 退款预览使用“可退余额”而非原订单金额，并排除已存在 pending/processing/completed 终态退款。
4. 管理后台明确展示“公益保留退款完成，报名资格已关闭”。

**必须新增测试**

- 公益保留退款后报名取消、名额释放、签到拒绝、空间拒绝。
- 退款完成后首次刷新、重新进入和“我的报名”列表返回同一业务状态。
- 同一订单不能再次申请公益保留退款。
- 并发提交只产生一个退款单。
- 公益账户仍保留 `¥4.95`，订单净收入与公益台账一致。

### P0-3 修复 H5 页面切换空引用

**现象**

页面路由切换时 uni-h5 的 activated hook 报：

```text
Cannot destructure property 'firstElementChild' of 'rootRef.value' as it is null
```

**整改方式**

1. 首先最小化复现：报名详情 -> 活动空间 -> 我的 -> 社交资料 -> 报名详情。
2. 检查近期新增 motion 包装是否改变页面根节点、在 activated 前移除节点或重复执行离场动画。
3. 页面根节点必须始终稳定存在；离场动画只能操作其子内容，组件卸载时执行 `gsap.context().revert()`。
4. H5 和小程序适配层禁止在页面卸载后继续访问 ref。
5. 加入路由循环 E2E，循环 20 次并断言无 console error。

## 三、P1 整改

### P1-1 前后端动作能力统一

- 服务端详情返回统一 `allowedActions`：`canRefund`、`canCancel`、`canCheckIn`、`canEnterSpace`。
- 用户端不再自行推断；已签到时不展示可执行退款按钮。
- 后端仍保留最终权限校验，避免绕过前端。

### P1-2 修复活动空间问答提交

- 对“提问 -> 发布”增加提交中、成功、失败状态和请求 ID。
- 发布成功后原地刷新问答，不跳回“我的”。
- 补充数据库落库、审核可见性、重复点击和登录失效测试。
- 检查通用弹层“发布”文本是否与页面/底栏点击事件发生错误匹配或冒泡。

### P1-3 修复图片选择取消状态

- `chooseImages()` 不应只依赖 Promise reject；为 H5 文件 input 的 `cancel`、窗口重新聚焦但无文件等分支统一结束 loading。
- 增加 15 秒保险超时，但超时只负责恢复 UI，不重复上传。
- H5 取消、微信相册取消、相机拒权、上传失败分别显示合适状态。
- 自动化断言取消后“添加照片”恢复可点击，提交按钮不被永久锁死。

### P1-4 统一 Asia/Shanghai 时间策略

- 修复 `scripts/seed-qiwai-demo.mjs`：禁止把本地目标时间 `toISOString()` 后去掉 `Z` 写入 DATETIME。
- API 契约统一返回带 `Z`/offset 的 ISO 8601，或明确所有 DATETIME 为上海时间；不能混用。
- 管理后台所有时间格式化显式指定 `timeZone: "Asia/Shanghai"`。
- 更新现有演示活动的错误时间，并加入“14:00 写入后 H5/后台都显示 14:00”测试。

### P1-5 经营指标使用有效状态

- 签到率默认使用未撤销核销记录。
- 另设“今日核销动作/撤销次数”用于审计，不与履约签到率混合。
- 撤销核销后看板、活动统计、名单应在同一刷新周期一致。

## 四、P2 整改

1. 将财务/订单代理筛选的空选项从 `undefined` 改为稳定字符串或 `null`，消除 Element Plus prop warning。
2. 将所有 `el-checkbox :label="value"` 迁移为 `:value="value"`。
3. 按角色过滤活动“更多”菜单；核销员只保留预览、复制链接、二维码等只读动作。
4. 系统设置标题按实际租户作用域显示，避免商家误改平台配置。
5. 继续拆分管理后台 `vendor` 与 Element Plus，目标单 chunk gzip 小于 200 kB。
6. 为所有提交动作统一“处理中、成功、失败、状态校验后重试”组件。

## 五、短信运营整改

当前报名提交和退款完成触发器已执行，但配置明确关闭。上线前按以下顺序处理：

1. 在商家短信设置中开启总开关。
2. 单独开启 `registrationSubmitted`、`paymentSucceeded`、`registrationApproved`、`refundSucceeded` 等需要的场景。
3. 配置短信供应商、签名、模板 ID 和变量映射。
4. 先向内部测试手机号发送单场景测试。
5. 在通知中心核对 `providerMessageId` 和最终送达回执，不以接口“已提交”代替送达成功。
6. 配置失败、余额不足和模板拒绝进入告警与人工重试队列。
