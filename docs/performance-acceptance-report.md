# 性能验收报告

## 1. 验收范围

本报告记录活动报名高峰、万级现场名单、后台分页查询和完整名单导出的可重复性能验收。商城库存并发、支付回调和退款并发使用各自专项脚本验证，不以本报告替代。

执行命令：

```powershell
$env:API_BASE='http://127.0.0.1:18080/api'
npm run acceptance:performance
```

验收脚本：`scripts/performance-acceptance.mjs`

结果文件：`.local-logs/performance-acceptance-1784193356594/result.json`

## 5. 数据库执行计划

MySQL `EXPLAIN ANALYZE` 结果：

- 活动资格名单统计使用 `IDX_registrations_activity_status_created` 覆盖索引范围扫描，10,100 行聚合约 5.67 ms。
- 100 行最新名单使用同一索引定位活动数据，限量排序后约 3.17 ms。
- 未核销统计使用报名复合索引和核销记录 `registrationId` 索引执行 antijoin，10,100 行约 12.4 ms。
- 核销表同时存在 `IDX_check_ins_registration_revoked_created(registrationId, revokedAt, createdAt)`，支持撤销状态和时间范围查询。

当前数据规模下无全表扫描或慢查询证据，不需要为了本批结果增加冗余索引。

### 6.1 缺陷与整改

第一次执行时，100 个单店订单只有 19 个成功，p95 约 48.54 秒；50 个跨店结算组只有 4 个成功。库存未超卖，但事务持有 SKU 锁后通过全局 Repository 再申请数据库连接，连接池被持锁事务占满，形成连接池饥饿。

积分查询改为复用当前事务 EntityManager 后，单店订单达到 100/100，但跨店仍有 14 个 MySQL 死锁。InnoDB 死锁图证明带关联的 `FOR UPDATE` 同时锁定 SKU、商品、商户和租户，不同执行计划形成“商户 B -> 租户”和“租户 -> 商户 B”的反向锁序。

最终整改：

- SKU 悲观锁只锁 `mall_skus` 主表目标行，不再锁整张关联图。
- 获取 SKU 锁后再以普通事务查询加载商品、店铺和租户数据，并以锁定行的库存值覆盖读取结果。
- 数据库死锁和锁等待统一返回可重试 409，不泄露底层 SQL 异常。
- `computeMallPointsQuote` 在订单事务内复用 EntityManager，禁止持锁时再次向连接池申请连接。
- 新增 migration `1783800000000-MallOrderPerformanceIndexes`，补齐订单号、业务幂等键唯一约束和订单热路径复合索引。

迁移前，会员商城订单查询扫描 218 行，约 0.62 ms；迁移后使用 `IDX_mall_orders_tenant_user_created` 覆盖索引，约 0.25 ms。过期订单扫描由主键扫描改为 `IDX_mall_orders_status_expires` 范围扫描，约 0.02 ms。

### 6.2 最终指标

| 场景 | 请求量 | p50 | p95 | 总耗时 | 吞吐 | 结果 |

| 单店报价 | 100 | 1,032.83 ms | 1,461.57 ms | 1,478.12 ms | 67.65 req/s | 100/100 |
| 单店热 SKU 下单 | 100 | 6,030.80 ms | 6,325.02 ms | 6,445.42 ms | 15.51 req/s | 100/100 |
| 跨店报价 | 50 | 522.09 ms | 697.41 ms | 701.01 ms | 71.33 req/s | 50/50 |
| 跨店拆单 | 50 组/100 子单 | 8,096.05 ms | 8,818.50 ms | 8,910.11 ms | 5.61 group/s | 50/50 |

SKU 118 在单店阶段锁定库存精确增加 100，在跨店阶段再增加 50；SKU 119 在跨店阶段精确增加 50。10 次跨店幂等重放全部返回原结算组，没有新增子单或重复锁库存。最终请求错误、500、409、死锁和锁等待均为 0。

最终备份为 756,780 bytes，GZip 完整解压 11,162,551 bytes。备份后按业务键复核为 100 个单店订单、50 个跨店组和 100 个跨店子订单；SKU 118/119 的 `stock/lockedStock` 分别为 `10159/309`、`10040/90`。

## 7. 结论与后续

本批万级名单、活动报名高峰和批量导出达到当前本地生产形态阈值，可以进入更高规模和生产环境复测。后续仍需完成：

- 生产规格主机上的持续压测、CPU/内存/连接池曲线及容量拐点。
- 真机弱网、相机扫码和多设备现场持续刷新。
- 正式对象存储、微信支付和短信供应商在生产网络下的端到端延迟。

因此，本报告只证明列出的性能场景通过，不代表全项目性能与生产验收全部完成。
